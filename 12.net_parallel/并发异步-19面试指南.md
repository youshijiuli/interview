## 2 并发与并行

### Q17: 什么是并发？什么是并行？

| 概念 | 定义 | 类比 |
|------|------|------|
| **并发（Concurrency）** | 在同一时间段内，多个任务交替执行，看起来像是同时执行，实际上是 CPU 快速切换 | 一个人同时处理多个项目，轮流做 |
| **并行（Parallelism）** | 在同一时刻，多个任务真正同时执行（需要多核 CPU） | 多个人同时处理多个项目 |

**关键区别：**
- 并发是逻辑上的同时，并行是物理上的同时
- 单核 CPU 可以实现并发，但不能实现并行
- 并行需要多核 CPU

**Python 中的体现：**
- **多线程（Threading）**：并发执行（受 GIL 限制）
- **多进程（Multiprocessing）**：并行执行（绕过 GIL）
- **协程（AsyncIO）**：并发执行（单线程内的协作式调度）

## 3 同步异步与阻塞非阻塞

### Q18: 同步 vs 异步，阻塞 vs 非阻塞的区别？

**答：** 这是两组不同维度的概念：

**同步 vs 异步（关注的是"消息通知机制"）：**
- **同步**：调用方主动等待结果返回。我调用一个函数，必须等它执行完才能继续
- **异步**：调用方不等结果，通过回调、事件通知等方式获取结果。我调用后可以去做别的事情

**阻塞 vs 非阻塞（关注的是"等待时的状态"）：**
- **阻塞**：调用结果返回前，当前线程被挂起，不能做其他事
- **非阻塞**：调用后立即返回，当前线程可以继续处理其他事情

**组合理解：**

| 组合 | 说明 | 示例 |
|------|------|------|
| 同步阻塞 | 等待时什么都不做 | 传统 Socket `recv()` |
| 同步非阻塞 | 轮询检查结果 | `select/poll` 检查是否可读 |
| 异步阻塞 | 等待回调但阻塞在事件循环 | select 阻塞等待事件 |
| 异步非阻塞 | 真正的高效模式 | I/O 完成端口、AsyncIO |

**面试记忆口诀：**
- 同步/异步：我打电话问书到了没有。同步=我一直拿着电话等答复；异步=我挂了电话，服务员到了给我打电话
- 阻塞/非阻塞：我在等待时能干嘛。阻塞=我原地发呆等；非阻塞=我边等边刷手机

### Q19: 进程间通信（IPC）有哪些方式？

| 方式 | 说明 |
|------|------|
| **管道（Pipe）** | 半双工通信，父子进程间使用 |
| **命名管道（FIFO）** | 可以在无亲缘关系进程间通信 |
| **消息队列** | 消息的链表，存放在内核中 |
| **共享内存** | 最快的 IPC 方式，多个进程共享一块内存 |
| **信号量（Semaphore）** | 用于同步和互斥 |
| **Socket** | 可用于不同机器之间的进程通信 |
| **信号（Signal）** | 通知进程发生了某个事件 |

### Q20: 正向代理和反向代理的区别？

| 维度 | 正向代理 | 反向代理 |
|------|---------|---------|
| **服务对象** | 为客户端服务 | 为服务端服务 |
| **典型用途** | 访问国外网站（翻墙）、隐藏客户端 IP | 负载均衡、隐藏服务器真实 IP |
| **客户端感知** | 客户端知道自己在使用代理 | 客户端以为自己直接访问的源站 |
| **示例** | VPN、Shadowsocks | Nginx、HAProxy |
| **配置位置** | 配置在客户端 | 配置在服务端 |

### Q21: TCP 粘包是什么？怎么解决？

**答：** TCP 粘包是指在 TCP 传输中，发送方发送的多个小数据包被接收方当成一个数据包接收的现象。

**原因：**
- TCP 是面向流的协议，没有消息边界
- 发送方启用了 Nagle 算法，合并小包发送
- 接收方没有及时读取缓冲区数据

**解决方案：**
1. **固定长度**：每个数据包固定大小，不够则填充
2. **分隔符**：在每个数据包末尾加上特殊分隔符（如 `\n`、`\r\n`）
3. **消息头 + 消息体**：在消息头部标明消息长度
4. **使用应用层协议**：如 HTTP 的 `Content-Length` 头

### Q22: HTTP 与 WebSocket 的区别？WebSocket 如何建立连接？

| 对比 | HTTP | WebSocket |
|------|------|-----------|
| 通信方式 | 请求-响应（半双工） | 全双工双向通信 |
| 连接 | 短连接（或长连接 Keep-Alive） | 长连接 |
| 服务端推送 | 需要轮询/long polling | 直接推送 |
| 开销 | 每次请求都要带完整 Header | 首次握手后，Header 很小 |
| 协议 | HTTP/1.1, HTTP/2 | ws://, wss:// |

**WebSocket 握手过程：**
```
客户端请求（Upgrade：告诉服务器要升级协议）：
GET /chat HTTP/1.1
Host: server.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

服务器响应（同意升级）：
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```
