# 06-网络编程

## 一、CS架构与BS架构

### 1.1 网络编程概述

网络编程就是编写程序，让两个或多个联网设备之间相互交换数据。在前面的学习过程中，我们是在本地开发应用，数据交互只能发生在本地。为了解决不同设备之间进行数据交互的问题，网络编程应运而生，它涉及不同的技术和协议。

常见的网络协议包括：
- **TCP/IP协议**：传输控制协议/因特网协议，控制数据在网络中传输的协议（图片/视频/文字等）
- **HTTP协议**：超文本传输协议，用于浏览器与服务器之间的通信
- **FTP协议**：文件传输协议，用于在网络上进行文件的上传和下载

**学习网络编程的目的**：理解客户端和服务端之间数据传输的基本原理，以便日后开发CS架构的模型。

### 1.2 CS架构

**C/S架构（Client/Server）** 即客户端与服务端模型，指的是用户安装的App和远程服务器构成的架构。例如手机上的王者荣耀、微信等应用。

**CS架构的优势**：
1. **应用服务器负载轻**：某些数据处理过程不会发生在服务端，减轻了服务端的压力。比如王者荣耀中很多英雄、地图、活动等资源都提前下载到本地，运行时从本地读取资源加载
2. **数据存储功能划分明确**：服务器只存储用户信息，本地存储应用资源

**CS架构的缺点**：
1. 维护成本高：需要聘请App开发工程师
2. 开发成本高：公司还需要运维人员
3. 升级麻烦：需要用户主动更新客户端

### 1.3 BS架构

**B/S架构（Browser/Server）** 即浏览器与服务端模型，用户通过浏览器访问网页（如京东、淘宝等）。

**BS架构的优势**：
1. **维护和升级成本较低**：只需一个运维维护服务器即可，升级也只需在服务器端操作
2. **成本较低，选择性更多**：服务器就是电脑硬件，可以选择不同平台的硬件

**BS架构的缺点**：
- 所有服务数据全部在服务器上，如果数据量太大会导致程序变慢

### 1.4 互联网的本质

互联网的本质就是一系列的协议，总称为"互联网协议"（Internet Protocol Suite）。互联网协议的功能是：定义计算机如何接入Internet，以及接入Internet的计算机通信的标准。

```python
# 网络编程的发展历程
# 1. 早期通信介质 --- 硬件设备（单机时代）
#    电脑只能自己使用，彼此之间相互独立

# 2. 早期通信介质 --- 网线（局域网时代）  
#    参考电话线原理，出现了网线，连接在一起的电脑可以数据交互
#    后来出现了交换机，有一个公共接口连接多个分接口

# 3. 互联网时代
#    网线介质局限在区域内，不同区域无法通信
#    将网线接入到大的介质中 --- 互联网诞生
#    为了统一不同设备之间数据交互的规范，出现了互联网协议

# 4. 互联网协议
#    定义了计算机如何接入Internet以及通信的标准
```

## 二、网络通信协议

### 2.1 OSI七层协议

OSI（Open System Interconnection）七层模型是国际标准化组织制定的网络通信标准框架：

| 层数 | 名称 | 功能描述 |
|------|------|----------|
| 第7层 | 应用层 | 向用户提供应用服务时通信的活动 |
| 第6层 | 表示层 | 数据格式化、数据加密 |
| 第5层 | 会话层 | 建立、管理、终止会话 |
| 第4层 | 传输层 | 定义传输数据的协议端口号，流控和差错校验 |
| 第3层 | 网络层 | 数据传输过程中的约束协议 |
| 第2层 | 数据链路层 | 网线、互联网介质 |
| 第1层 | 物理层 | 硬件设备的零件 |

### 2.2 TCP/IP五层协议

TCP/IP五层协议将OSI的会话层、表示层合并到应用层，形成更实用的五层模型：

| 层数 | 名称 | 核心功能 |
|------|------|----------|
| 第5层 | 应用层 | 所有的数据展示和建立管理会话 |
| 第4层 | 传输层 | 数据的传输（TCP/UDP） |
| 第3层 | 网络层 | 数据传输过程中的约束协议（IP） |
| 第2层 | 数据链路层 | 网线、互联网介质（MAC、以太网） |
| 第1层 | 物理层 | 硬件设备的零件 |

### 2.3 各层详细解析

#### 2.3.1 物理层

物理层是OSI模型的底层，构成不同设备之间组网的基础。计算机是基于电工作的，分为高低电频，对应二进制数据的0和1。

```python
# 物理层核心概念
# - 传输介质：网线、光纤、无线信号
# - 信号类型：电信号、光信号
# - 数据形式：0和1的二进制比特流
```

#### 2.3.2 数据链路层

数据链路层定义了0/1数据如何在网线中传输。它对电信号进行规范约束，确定每一串01代码代表的含义。

**(1) 以太网协议（Ethernet）**

早期每个公司都有自己的分组方式（局域网），后来统一了标准，形成以太网协议。一组电信号就是一个数据包（帧），帧包括：
- **头（head）**：包含发送者源地址(6字节) + 接收者目的地址(6字节) + 数据类型(2字节)
- **数据包（data）**：具体的内容（最短46字节，最长1500字节）

**(2) MAC地址**

每台接入互联网的设备必须具备网卡，网卡中存储着发送者地址和接收者地址（即MAC地址）。MAC地址的特点：
- 每块网卡在出厂时都会烧制世界上唯一的MAC地址
- 长度 48 位二进制（用 12 个十六进制字符表示）：前 24 位（6 个十六进制字符）是厂商编号（OUI），后 24 位（6 个十六进制字符）是序列号
- 例如：`00:16:3e:1a:83:a0`

**(3) 广播**

有了MAC地址后，多台设备接入同一个局域网中，采用最原始的数据交互方式"广播"来查找目标地址。每一台设备检查自己的MAC地址与目标地址是否一致，一致就接收，不一致就丢弃。

```python
# 数据链路层关键概念总结
# 1. 以太网协议：局域网数据交互的标准（ethernet）
# 2. MAC地址：网卡的唯一标识，12位16进制数
# 3. 广播：在局域网内靠"吼"来找到目标设备
```

#### 2.3.3 网络层

网络层的作用是引入一套新的交互技术，实现不同局域网之间的数据交互。

**(1) IP协议**

规定网络地址的协议就是IP地址。现在广泛采用的是IPv4，由32位二进制表示，范围是`0.0.0.0 ~ 255.255.255.255`，通常由四段十进制数表示，例如`192.168.1.96`。

**(2) IP地址的组成部分**

- **网络部分**：表示子网
- **主机部分**：表示主机

注意：单纯的IP地址只是标识了IP地址的种类，仅从网络部分或主机部分无法识别IP所处的子网。例如`172.16.10.1`和`176.16.10.2`的网络部分都是`172.16.10.0`，但不一定在同一个局域网下。

**(3) 子网掩码**

子网掩码用来标识一个IP地址的网络部分和主机部分。在形式上等同于IP地址，也是32位二进制数字，网络部分用1表示，主机部分全是0。例如子网掩码`255.255.255.0`的二进制表示为：
```
11111111.11111111.11111111.00000000
```

通过子网掩码可以判断两个IP地址是否处于同一个局域网下。

**(4) ARP协议**

ARP协议通过广播方式发送数据包，获取目标MAC地址。在所有上层的数据包最后都需要封装一个以太网头，再通过以太网发送。在发包时获取自己的源MAC地址很容易，但要获取对方的MAC地址，就得通过ARP协议来完成。

```python
# 网络层关键概念总结
# 1. IP协议：规定网络地址的协议（IPv4: 32位，IPv6: 128位）
# 2. IP地址组成：网络部分 + 主机部分
# 3. 子网掩码：区分IP地址的网络地址和主机地址
# 4. ARP协议：通过广播获取目标MAC地址
# 5. IP数据包：head(20-60字节) + data(最高65515字节)
```

#### 2.3.4 传输层

网络层的IP帮助我们区分互联网中的不同设备（通过MAC地址），但一台设备上可能同时运行多个应用程序（QQ、微信、浏览器等）。虽然能找到目标设备，但如何区分信息是发给哪个应用程序的呢？

于是诞生了传输层技术 -- **端口（Port）**。不同应用程序运行在不同的端口上：
- 端口1314：alist页面
- 端口80：nginx页面  
- 端口8008：QQ
- 端口8009：微信

**端口范围**：0 - 65535，其中 0-1023 是系统占用的端口。

#### 2.3.5 应用层

应用层规定了应用程序之间传输数据的格式。TCP协议可以为各种程序传递数据，但具体的数据加密过程由当前程序决定。

```python
# 五层协议数据封装流程
# 应用层：原始数据
#    ↓
# 传输层：TCP/UDP头 + 数据
#    ↓
# 网络层：IP头 + TCP/UDP头 + 数据
#    ↓
# 数据链路层：MAC头 + IP头 + TCP/UDP头 + 数据 + 校验
#    ↓
# 物理层：转换为电信号/光信号传输
```

## 三、TCP协议与UDP协议对比

### 3.1 TCP协议（传输控制协议）

TCP是一种**可靠的、面向连接的**传输协议，也叫流式协议。

**特点**：
- 传输数据的过程像流水一样，可以不间断地传输数据
- 理论上数据可以无限大，但有一定限制
- 数据包之间有序，保证数据完整到达
- 需要建立连接（三次握手）和断开连接（四次挥手）

### 3.2 UDP协议（用户数据报协议）

UDP是一种**不可靠的、无连接的**传输协议，也叫报式协议。

**特点**：
- 传输数据的过程像报文一样，数据包之间没有关联，独立传输
- 类似快递员送快递，快递与快递之间没有关联
- 传输速度快，但不保证数据一定到达
- 适用于实时通信场景（视频通话、直播等）

### 3.3 TCP与UDP对比

| 对比项 | TCP | UDP |
|--------|-----|-----|
| 连接方式 | 面向连接 | 无连接 |
| 可靠性 | 可靠传输，保证数据完整 | 不可靠传输，可能丢包 |
| 传输方式 | 流式协议 | 报式协议 |
| 速度 | 较慢 | 较快 |
| 应用场景 | 文件传输、网页浏览、邮件 | 视频通话、直播、DNS查询 |
| 握手过程 | 三次握手建立，四次挥手断开 | 无需握手 |

## 四、三次握手与四次挥手

三次握手和四次挥手是TCP协议中保证可靠连接的核心机制。

### 4.1 三次握手（建立连接）

三次握手发生在TCP建立连接的过程中，目的是确保客户端和服务端双方都能收发数据。

#### 握手过程详解

**第一次握手（客户端 -> 服务端）**：
- 客户端向服务端发送SYN包：`SYN=1, seq=x`（x为随机数）
- 客户端发送后进入 **SYN_SENT** 状态（此时服务端尚未收到，仍处于 LISTEN 状态）

**第二次握手（服务端 -> 客户端）**：
- 服务端收到 SYN 包后，回复确认并发送自己的连接请求：`SYN=1, ACK=1, seq=y, ack=x+1`
- 服务端发送后进入 **SYN_RCVD** 状态

**第三次握手（客户端 -> 服务端）**：
- 客户端收到 SYN+ACK 后，进入 **ESTABLISHED** 状态
- 并发送确认包：`ACK=1, seq=x+1, ack=y+1`
- 服务端收到 ACK 后进入 **ESTABLISHED** 状态
- 连接建立成功

#### 生活化比喻（相亲）

```
第一次表白（男→女）：我想跟你处对象（SYN=1），我是张三（seq=x）
第二次表白（女→男）：我知道你想跟我处对象（ACK=1，ack=x+1），
                    我也想跟你处对象（SYN=1），我是李四（seq=y）
第三次表白（男→女）：我知道你想跟我处对象（ACK=1，ack=y+1），
                    咱们在一起吧！
```

#### 为什么需要三次握手？

三次握手的目的是：
1. 确认双方都能收发数据
2. 防止已失效的连接请求报文突然传到服务端，产生错误
3. 通过随机数和序列号防止过期连接被错误接受

### 4.2 四次挥手（断开连接）

四次挥手发生在TCP断开连接的过程中，因为是全双工通信，双方都需要关闭。

#### 挥手过程详解

**第一次挥手（客户端 -> 服务端）**：
- 客户端发送FIN包：`FIN=1, seq=u`
- 客户端进入 **FIN_WAIT_1** 状态

**第二次挥手（服务端 -> 客户端）**：
- 服务端回复ACK包：`ACK=1, seq=v, ack=u+1`
- 服务端进入 **CLOSE_WAIT** 状态
- 客户端收到后进入 **FIN_WAIT_2** 状态

**第三次挥手（服务端 -> 客户端）**：
- 服务端发送FIN包：`FIN=1, ACK=1, seq=w, ack=u+1`
- 服务端进入 **LAST_ACK** 状态

**第四次挥手（客户端 -> 服务端）**：
- 客户端发送ACK包：`ACK=1, seq=u+1, ack=w+1`
- 客户端进入 **TIME_WAIT** 状态（等待2MSL后关闭）
- 服务端收到后关闭连接

#### 生活化比喻（分手/搬家）

```
第一次分手（男→女）：我们分手吧（FIN=1，这是第X次提分手）
第二次分手（女→男）：知道了，但我东西还没收拾好，先别分（ACK=1，收到第X+1次）
第三次分手（女→男）：东西收拾好了，可以分了（FIN=1，我是认真的）
第四次分手（男→女）：知道了，分吧（ACK=1）
```

### 4.3 连接过程中的状态

**服务端状态**：
- **LISTEN**：等待连接请求
- **SYN_RCVD**：已收到 SYN，已发送 SYN+ACK，等待对端确认
- **ESTABLISHED**：连接已建立，正常传输数据
- **CLOSE_WAIT**：被动关闭方收到对端 FIN 并已 ACK，等待本地应用层 close
- **LAST_ACK**：被动关闭方已发送自己的 FIN，等待对端最终 ACK
- **CLOSED**：连接彻底关闭

> 说明：状态分布按"主动/被动"区分更准确。主动关闭方会经历 FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT；被动关闭方会经历 CLOSE_WAIT → LAST_ACK。客户端和服务端均可作为主动关闭方。

**客户端状态**：
- **SYN_SENT**：已发送连接请求，等待匹配
- **ESTABLISHED**：连接已建立
- **FIN_WAIT_1**：主动关闭方发送 FIN 后的状态
- **FIN_WAIT_2**：收到对方对 FIN 的 ACK，等待对方的 FIN
- **TIME_WAIT**：收到对方 FIN 并回复 ACK 后，等待 2MSL 确保 ACK 到达对端

### 4.4 DDoS攻击与防范

**DDoS攻击原理**：
- 攻击者利用大量"肉鸡"在同一时间发送大量SYN连接请求
- 服务端收到大量SYN请求，一直处于SYN_RCVD状态
- 服务端无法完成所有三次握手，资源耗尽
- 合法用户无法建立连接

```python
# DDoS攻击模拟（仅供学习理解，请勿用于非法用途）
import socket
import threading

target_ip = "127.0.0.1"
target_port = 8080

def attack():
    while True:
        client_socket = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
        client_socket.connect((target_ip, target_port))

for _ in range(50):
    t = threading.Thread(target=attack)
    t.start()
```

**防御策略**：
1. 增加网络带宽
2. 限制连接频率
3. 过滤恶意流量（使用IDS/IPS）
4. 使用反向代理缓存
5. 合理配置防火墙规则
6. 使用CDN服务
7. 搭建高可用架构
8. 实施流量分析和监控
9. 手动或自动启用黑名单

## 五、Socket编程

### 5.1 Socket概念

Socket是应用层与TCP/IP协议族通信的中间软件抽象层，它是一组接口。在设计模式中，Socket就是一个门面模式，把复杂的TCP/IP协议族隐藏在Socket接口后面。

- **IP地址**：标识互联网中一台主机的位置
- **端口号（Port）**：标识这台机器上的一个应用程序
- **IP+Port**：标识互联网中独一无二的一个应用程序
- **进程号（PID）**：同一台机器上不同进程或线程的标识

### 5.2 套接字类型

**(1) 基于文件型的套接字**：`AF_UNIX`
- 一切皆文件，基于文件的套接字模型，用底层文件系统获取数据
- 用于同一台主机上进程间通信（IPC）

**(2) 基于网络型的套接字**：`AF_INET`
- 用于不同主机之间的网络通信
- python支持多种地址家族，最常用的是AF_INET

### 5.3 Socket工作流程

以打电话模型来说明：

**服务端（接电话方）**：
1. 拥有一台手机（创建socket对象）
2. 插上电话卡（绑定IP和端口 bind）
3. 开启手机等待来电（监听 listen）
4. 接听电话（接受连接 accept）
5. 接收对方信息（接收数据 recv）
6. 回复信息（发送数据 send）
7. 挂断电话（关闭连接 close）

**客户端（打电话方）**：
1. 拥有一台手机（创建socket对象）
2. 插上电话卡（系统自动分配端口）
3. 知道对方号码（指定服务端IP和端口）
4. 拨打电话（发起连接 connect）
5. 与对方交流（发送数据 send）
6. 听到对方信息（接收数据 recv）
7. 挂断电话（关闭连接 close）

### 5.4 TCP服务端与客户端

#### 基础版本（单次通信）

**服务端代码**：

```python
import socket

# 1. 创建socket对象
# family: 套接字家族（AF_INET 基于网络型）
# type: 套接字类型（SOCK_STREAM TCP流式协议）
server = socket.socket(family=socket.AF_INET, type=socket.SOCK_STREAM)

# 2. 绑定IP和端口
server.bind(("127.0.0.1", 9696))
```

## 六、粘包问题及解决方案

### 6.1 粘包问题原理

粘包问题只在**TCP协议**中产生，UDP协议不存在此问题。原因在于：

- **UDP是报式协议**：每次发送的数据是独立的数据包，接收方按包接收
- **TCP是流式协议**：发送的数据封装成数据包发送，数据像流水一样连续传输

**粘包场景**：
```
服务端发送 1GB 数据 -> 客户端每次只能接收 500MB
-> 剩余 500MB 数据会与下一次发送的数据粘在一起
```

```
比如发送 "1234567" -> 接收 "12345" (接收了前5个字节)
下一次发送 "8912345" -> 接收 "67891" (先收到上次剩余的 67 + 本次的前 891)
```

### 6.2 粘包问题演示（远程命令执行场景）

```python
# 客户端发送命令（如 ifconfig），服务端执行并返回结果
# 返回结果可能很大（超过1024字节），导致粘包
```

### 6.3 解决思路

**思路一**：增大客户端缓冲区
```python
# 将 recv(1024) 改为 recv(2048) 或更大
# 但无法从根本上解决问题，因为无法预知数据量
```

**思路二**：先告诉客户端数据总量，再发送数据（推荐）
1. 服务端计算要发送数据的总大小
2. 先将数据大小发送给客户端
3. 再发送实际数据
4. 客户端先接收数据大小，再循环接收直到收完所有数据

### 6.4 使用struct模块解决粘包

`struct`模块可以将整数打包成固定长度的二进制数据（用`i`模式打包成4字节），解决"如何告诉对方数据大小"的问题。

```python
import struct

# 打包：将整数转为4字节的二进制数据
data_length = 4315
packed_data = struct.pack('i', data_length)
print(packed_data)  # b'\xdb\x10\x00\x00'

# 解包：将4字节二进制数据转回整数
original_length = struct.unpack('i', packed_data)[0]
print(original_length)  # 4315
```

**struct常用格式字符**：

| 格式 | 类型 | 字节数 |
|------|------|--------|
| `x` | 填充字节 | 1 |
| `c` | char | 1 |
| `b` | signed char | 1 |
| `B` | unsigned char | 1 |
| `h` | short | 2 |
| `H` | unsigned short | 2 |
| `i` | int | 4 |
| `I` | unsigned int | 4 |
| `l` | long | 4或8 |
| `q` | long long | 8 |
| `f` | float | 4 |
| `d` | double | 8 |
| `?` | bool | 1 |

### 6.5 服务端（解决粘包）

```python
import socket
import subprocess
import struct

def run_cmd(cmd):
    """执行shell命令并返回结果"""
    obj = subprocess.Popen(
        cmd,
        shell=True,
        stdout=subprocess.PIPE,
        stderr=subprocess.PIPE,
        encoding="utf-8"
    )
    true_result = obj.stdout.read()
    false_result = obj.stderr.read()
    return true_result if true_result else false_result

server = socket.socket(family=socket.AF_INET, type=socket.SOCK_STREAM)
server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
server.bind(("127.0.0.1", 9696))
server.listen(5)

while True:
    client_socket, client_addr = server.accept()
    print(f"客户端地址：{client_addr}")
    while True:
        try:
            data_from_client = client_socket.recv(1024)
            if not data_from_client:
                break
            cmd = data_from_client.decode()
            if cmd == "q":
                break
            print(f"执行命令：{cmd}")

            # 获取命令执行结果
            result = run_cmd(cmd)
            result_bytes = result.encode("utf-8")

            # 计算数据大小并用struct打包
            data_length = len(result_bytes)
            packed_length = struct.pack('i', data_length)

            # 先发送4字节的数据大小，再发送实际数据
            client_socket.send(packed_length)
            client_socket.send(result_bytes)

        except Exception as e:
            break
    client_socket.close()
server.close()
```

### 6.6 客户端（解决粘包）

```python
import socket
import struct

client = socket.socket()
client.connect(("127.0.0.1", 9696))

while True:
    cmd = input("请输入命令：").strip()
    if not cmd:
        continue
    client.send(cmd.encode("utf-8"))
    if cmd == "q":
        break

    # 1. 先接收4字节的数据大小
    packed_length = client.recv(4)
    data_length = struct.unpack('i', packed_length)[0]
    print(f"数据总长度：{data_length}")

    # 2. 循环接收直到收完所有数据
    received_size = 0
    total_data = b""
    buffer_size = 1024
    while received_size < data_length:
        # 每次最多读 buffer_size，但末段不足时 recv 返回更少
        chunk = client.recv(min(buffer_size, data_length - received_size))
        if not chunk:
            break  # 对端关闭连接
        total_data += chunk
        received_size += len(chunk)  # 必须按实际接收长度累加

    print(f"命令结果：\n{total_data.decode()}")

client.close()
```

### 6.7 使用json+struct传递元信息（文件传输示例）

当需要传输文件时，除了数据大小，还需传递文件名、MD5校验值等元信息。可用JSON+struct组合。

**服务端（发送文件）**：

```python
import socket
import struct
import json
import hashlib
import os

def read_data(file_name):
    file_path = os.path.join(os.path.dirname(__file__), file_name)
    with open(file_path, "rb") as fp:
        return fp.read()

server = socket.socket(family=socket.AF_INET, type=socket.SOCK_STREAM)
server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
server.bind(("127.0.0.1", 9696))
server.listen(5)

while True:
    client_socket, client_addr = server.accept()
    print(f"客户端地址：{client_addr}")
    while True:
        try:
            file_name = client_socket.recv(1024).decode()
            if file_name == "q":
                break

            file_data = read_data(file_name + ".png")

            # 计算MD5校验值
            md5 = hashlib.md5()
            md5.update(file_data)

            # 构建元信息字典
            file_info = {
                "file_name": file_name,
                "file_type": "png",
                "file_hex": md5.hexdigest(),
                "data_all": len(file_data)
            }

            # 将元信息转为JSON字符串再编码
            info_json = json.dumps(file_info)
            info_bytes = info_json.encode("utf-8")

            # 打包元信息长度
            packed_info_len = struct.pack('i', len(info_bytes))

            # 依次发送：元信息长度 -> 元信息 -> 文件数据
            client_socket.send(packed_info_len)
            client_socket.send(info_bytes)
            client_socket.send(file_data)

        except Exception as e:
            break
    client_socket.close()
```

**客户端（接收文件）**：

```python
import socket
import struct
import json
import hashlib
import os

client = socket.socket()
client.connect(("127.0.0.1", 9696))

while True:
    file_name = input("请输入文件名：").strip()
    if not file_name:
        continue
    client.send(file_name.encode("utf-8"))
    if file_name == "q":
        break

    # 1. 接收元信息长度（4字节）
    packed_len = client.recv(4)
    info_len = struct.unpack("i", packed_len)[0]

    # 2. 接收元信息JSON
    file_info = json.loads(client.recv(info_len))
    data_length = file_info.get("data_all")
    old_md5 = file_info.get("file_hex")
    print(f"文件大小：{data_length} 字节")

    # 3. 循环接收文件数据
    received_size = 0
    file_data = b""
    buffer_size = 1024
    while received_size < data_length:
        chunk = client.recv(min(buffer_size, data_length - received_size))
        if not chunk:
            break  # 对端关闭连接
        file_data += chunk
        received_size += len(chunk)  # 必须按实际接收长度累加

    # 4. 校验文件完整性
    md5 = hashlib.md5()
    md5.update(file_data)
    if md5.hexdigest() != old_md5:
        print("文件已损坏！")
        break

    # 5. 保存文件
    save_name = "nb_" + file_info.get("file_name") + "." + file_info.get("file_type")
    save_path = os.path.join(os.path.dirname(__file__), save_name)
    with open(save_path, "wb") as fp:
        fp.write(file_data)
    print(f"文件已保存至：{save_path}")
```

### 8.1 UDP通信循环（完整版）

```python
from socket import socket, AF_INET, SOCK_DGRAM

# 创建UDP服务端
server = socket(family=AF_INET, type=SOCK_DGRAM)
server.bind(("127.0.0.1", 9696))

print("UDP服务端已启动，等待客户端消息...")

while True:
    # 接收客户端数据（recvfrom返回数据和客户端地址）
    data, client_addr = server.recvfrom(1024)
    msg = data.decode()
    print(f"收到来自 {client_addr} 的消息: {msg}")

    if msg == "q":
        print("客户端请求断开连接")
        continue

    # 回复客户端（将消息转为大写）
    reply = msg.upper()
    server.sendto(reply.encode("utf-8"), client_addr)
```

## 九、补充知识：HTTP协议简述

### 9.1 什么是HTTP

HTTP（HyperText Transfer Protocol，超文本传输协议）是应用层协议，基于TCP协议之上。它是Web浏览器和Web服务器之间通信的基础协议。

**HTTP的特点**：
- 无状态：每次请求都是独立的，服务器不会记录之前的请求信息
- 基于请求-响应模型：客户端发送请求，服务器返回响应
- 支持多种请求方法：GET、POST、PUT、DELETE等

### 9.2 HTTP请求与响应格式

**HTTP请求格式**：
```
GET /index.html HTTP/1.1
Host: www.example.com
User-Agent: Mozilla/5.0
Accept: text/html

请求体（POST时）
```

**HTTP响应格式**：
```
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1234

<html>...</html>
```

### 9.3 常见HTTP状态码

| 状态码 | 含义 | 说明 |
|--------|------|------|
| 200 | OK | 请求成功 |
| 301 | Moved Permanently | 永久重定向 |
| 302 | Found | 临时重定向 |
| 304 | Not Modified | 资源未修改，使用缓存 |
| 400 | Bad Request | 请求格式错误 |
| 403 | Forbidden | 禁止访问 |
| 404 | Not Found | 资源未找到 |
| 500 | Internal Server Error | 服务器内部错误 |
| 502 | Bad Gateway | 网关错误 |
| 503 | Service Unavailable | 服务不可用 |

### 9.4 使用Socket模拟HTTP请求


## 十、网络编程常见面试题

### 10.1 基础概念题

**Q1: 什么是Socket？Socket的工作原理是什么？**

Socket是应用层与TCP/IP协议族通信的中间软件抽象层，它是一组接口。它对用户隐藏了复杂的TCP/IP协议细节，提供简单的接口来组织数据以符合指定协议。Socket的本质就是IP地址+端口号的组合，用于唯一标识网络中的一个应用程序。

**Q2: TCP协议和UDP协议的区别？**

| 对比维度 | TCP | UDP |
|----------|-----|-----|
| 连接方式 | 面向连接 | 无连接 |
| 可靠性 | 可靠（确认/重传/校验） | 不可靠 |
| 传输方式 | 流式（按字节流） | 报式（按数据报） |
| 速度 | 慢 | 快 |
| 头部开销 | 20字节 | 8字节 |
| 应用场景 | HTTP、FTP、SMTP | DNS、直播、VoIP |

**Q3: 简述OSI七层模型和TCP/IP五层模型的对应关系？**

OSI七层：物理层、数据链路层、网络层、传输层、会话层、表示层、应用层
TCP/IP五层：物理层、数据链路层、网络层、传输层、应用层（合并了会话层和表示层）

**Q4: 什么是IP地址？IPv4和IPv6的区别？**

IP地址是互联网中设备的唯一标识。IPv4由32位二进制组成（如192.168.1.1），IPv6由128位二进制组成（如2001:0db8:85a3::8a2e:0370:7334）。IPv6主要是为了解决IPv4地址枯竭问题而设计的。

### 10.2 深入理解题

**Q6: 详细描述三次握手过程，为什么需要三次而不是两次？**

三次握手的过程：
1. 客户端发送SYN=1, seq=x（请求建立连接）
2. 服务端回复SYN=1, ACK=1, seq=y, ack=x+1（同意连接并请求确认）
3. 客户端回复ACK=1, seq=x+1, ack=y+1（确认连接）

为什么需要三次而不是两次：两次握手只能确认客户端到服务端的信道正常，无法确认服务端到客户端的信道正常。三次握手能确保双方都能收发数据，同时防止已过期的连接请求到达服务端产生错误连接。

**Q7: 详细描述四次挥手过程，为什么是四次而不是三次？**

四次挥手的过程：
1. 客户端发送FIN=1, seq=u（请求断开连接）
2. 服务端回复ACK=1, ack=u+1（确认收到断开请求，但可能还有数据未传完）
3. 服务端发送FIN=1, seq=w, ack=u+1（数据传输完成，请求断开）
4. 客户端回复ACK=1, ack=w+1（确认断开）

为什么是四次：TCP是全双工通信，客户端和服务端都可以主动关闭连接。当客户端请求断开时，服务端可能还有数据未发送完毕，所以需要"确认收到（ACK）"和"数据发完请求断开（FIN）"分两步进行。如果服务端在收到FIN时也没有数据要发送，可以将第二次和第三次合并。

**Q8: 什么是粘包问题？如何解决？**

粘包问题：在TCP流式传输中，发送方连续发送的数据可能在接收方合并接收，或者一次发送的大数据被分多次接收，导致数据边界混乱。

解决方式：
1. 使用`struct`模块将数据长度打包成固定4字节，先发送长度再发送数据
2. 结合`json`传递元信息（文件名、MD5校验值等）
3. 使用自定义的"结束标志"来定界（不适合二进制数据）
4. 使用固定长度协议（每条消息固定长度，不足则填充）

**Q9: TIME_WAIT状态的作用是什么？**

TIME_WAIT状态发生在主动关闭连接的一方（通常是客户端），在发送完最后一次ACK后进入，持续时间为2MSL（Maximum Segment Lifetime，报文最大生存时间的两倍）。作用：
1. 确保最后一个ACK能够到达服务端（如果丢失，服务端会重发FIN，客户端可以重发ACK）
2. 使本连接持续时间内产生的所有报文都从网络中消失，防止影响新连接

### 10.3 实践应用题

**Q10: 如何用Python实现一个支持多客户端并发的TCP服务端？**

```python
import socket
from threading import Thread

def handle_client(conn, addr):
    print(f"客户端 {addr} 已连接")
    while True:
        try:
            data = conn.recv(1024)
            if not data:
                break
            print(f"{addr}: {data.decode()}")
            conn.send(f"收到: {data.decode()}".encode())
        except Exception:
            break
    conn.close()
    print(f"客户端 {addr} 已断开")

server = socket.socket()
server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
server.bind(("0.0.0.0", 8888))
server.listen(128)

print("服务器启动，等待客户端连接...")
while True:
    conn, addr = server.accept()
    Thread(target=handle_client, args=(conn, addr)).start()
```

**Q11: ARP协议的作用是什么？工作原理？**

ARP（Address Resolution Protocol）地址解析协议，用于通过IP地址获取对应的MAC地址。

工作原理：
- 当主机A要向局域网内的主机B发送数据时，先检查自己的ARP缓存表
- 如果没有B的MAC地址，A会向局域网内广播ARP请求包（包含B的IP地址）
- 网络中的所有主机收到请求后检查是否与自己IP匹配
- 主机B匹配成功后向A发送ARP响应包（包含自己的MAC地址）
- A收到后将B的IP-MAC映射存入ARP缓存，然后进行通信
